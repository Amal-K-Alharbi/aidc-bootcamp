# Lab W3D3 — The Engine Swap

## Overview

In this lab, I replaced the Week 2 inference engine with **vLLM** while keeping the same OpenAI-compatible `/v1` API.

The goal was to compare **vLLM continuous batching** with Monday's static batching under different concurrency levels.

## Prediction Card

Before running the benchmark:

* Monday static batch-8 vs vLLM throughput: **2.5×**
* Monday static batching scaling (1 → 8): **2.80×**
* Predicted vLLM scaling (1 → 8): **3×**
* Expected vLLM scaling compared with static batching: **larger**

## Results

| Concurrency | Static Batching |               vLLM |   Speedup |
| ----------- | --------------: | -----------------: | --------: |
| 1           |   34.9 tokens/s |      59.4 tokens/s |     1.70× |
| 4           |   51.0 tokens/s |     162.9 tokens/s |     3.19× |
| 8           |   97.7 tokens/s | **235.9 tokens/s** | **2.41×** |

### Scaling

* Static batching: **2.80×**
* vLLM: **3.97×**
* Scaling advantage: **1.42×**

## Conclusion

vLLM achieved **235.9 tokens/s at concurrency 8**, which is **2.41× faster** than Monday's static-batching baseline.

The main lesson is that **continuous batching scales better than static batching** because finished requests can be replaced by waiting requests instead of leaving batch slots idle.

# Extra W3D3 — Load Shedding Under Overload

## Card

* **Objective:** Protect latency under overload using client-side admission control.
* **Server:** vLLM
* **Model:** Qwen/Qwen2.5-1.5B-Instruct
* **GPU:** NVIDIA T4
* **Burst:** 50 requests
* **Load-shedding cap:** 8 in-flight requests

## Naive vs Load Shedding

| Test                  | Requests | Accepted | Shed | p95 Latency |
| --------------------- | -------: | -------: | ---: | ----------: |
| Naive unbounded       |       50 |       50 |    0 |     0.901 s |
| Load shedding (cap 8) |       50 |        8 |   42 |     0.433 s |

Load shedding reduced accepted-request p95 latency from **0.901 s to 0.433 s** while rejecting excess requests immediately.

## Burst Sweep

| Burst | Accepted | Shed | Accepted p95 |
| ----: | -------: | ---: | -----------: |
|     8 |        8 |    0 |      0.382 s |
|    16 |        8 |    8 |      0.391 s |
|    32 |        8 |   24 |      0.402 s |
|    50 |        8 |   42 |      0.377 s |

The accepted p95 stayed approximately flat as the burst increased, while the number of shed requests increased.

## Conclusion

Load shedding prevents requests from building up in an uncontrolled queue. With a cap of 8, only 8 requests were admitted at a time and excess requests were rejected immediately.
