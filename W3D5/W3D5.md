# Benchmark Configuration

The benchmark was executed using:

```bash
python bench.py \
  --base-url http://localhost:8000 \
  --model Qwen/Qwen2.5-1.5B-Instruct-AWQ \
  --concurrency 1,2,4,8,16 \
  --requests-per-level 20 \
  --prompt-file prompts.txt \
  --out bench_report.json
```

Each concurrency level used 20 requests from the provided fixed prompt set.

# Knee Determination

The selected p95 SLO was **2.0 seconds**.

Concurrency 8 achieved:

* **473.88 tokens/s**
* **1.944 s p95 latency**
* **0 errors**

Concurrency 16 achieved higher throughput:

* **670.76 tokens/s**

However, its p95 latency increased to **2.489 seconds**, exceeding the 2.0-second SLO.

Therefore:

> **Knee concurrency = 8**

This is the highest tested concurrency that remains within the selected p95 latency target.

---

# Capacity Decision

The recommended sustainable operating point is:

**8 concurrent requests**

At this operating point:

* **Maximum sustainable throughput:** 473.88 tokens/s
* **p95 latency:** 1.944 s
* **Target p95:** 2.0 s
* **Errors:** 0

Concurrency 16 can provide higher peak throughput, but it does not satisfy the selected latency SLO.

---

# Limiting Factor

The benchmark indicates a **compute/queueing saturation** pattern.

As concurrency increases, aggregate throughput continues to improve, but tail latency increases significantly. The jump from concurrency 8 to 16 increases p95 latency from **1.944 s to 2.489 s**, crossing the SLO.

This suggests that the system is approaching a saturation point where additional concurrent requests create increased contention and queueing.
