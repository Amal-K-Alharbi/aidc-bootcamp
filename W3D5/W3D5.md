# Benchmark Configuration

The benchmark was executed using:

```bash
python bench.py \
  --base-url http://localhost:8000 \
  --model Qwen/Qwen2.5-1.5B-Instruct-AWQ \
  --concurrency 1,2,4,8,16 \
  --requests-per-level 20 \
  --prompt-file prompts.txt \
  --out bench_report.json
```

Each concurrency level used 20 requests from the provided fixed prompt set.

# Knee Determination

The selected p95 SLO was **2.0 seconds**.

Concurrency 8 achieved:

* **473.88 tokens/s**
* **1.944 s p95 latency**
* **0 errors**

Concurrency 16 achieved higher throughput:

* **670.76 tokens/s**

However, its p95 latency increased to **2.489 seconds**, exceeding the 2.0-second SLO.

Therefore:

> **Knee concurrency = 8**

This is the highest tested concurrency that remains within the selected p95 latency target.

---

# Capacity Decision

The recommended sustainable operating point is:

**8 concurrent requests**

At this operating point:

* **Maximum sustainable throughput:** 473.88 tokens/s
* **p95 latency:** 1.944 s
* **Target p95:** 2.0 s
* **Errors:** 0

Concurrency 16 can provide higher peak throughput, but it does not satisfy the selected latency SLO.

---

# Limiting Factor

The benchmark indicates a **compute/queueing saturation** pattern.

As concurrency increases, aggregate throughput continues to improve, but tail latency increases significantly. The jump from concurrency 8 to 16 increases p95 latency from **1.944 s to 2.489 s**, crossing the SLO.

This suggests that the system is approaching a saturation point where additional concurrent requests create increased contention and queueing.

# Extra W3D5 — Cost per Million Tokens & Scale-Out Breakeven

## Prediction Card

**Cost:** I predict that cost per 1M tokens will decrease as throughput increases because the GPU hourly cost is spread across more tokens.

**Scale-out:** If approximately 2× the knee throughput is required, I predict that adding a second GPU at the same safe knee concurrency will be preferable to pushing one GPU beyond the SLO.

**Outcome:** Prediction confirmed. The knee was **C8 / 473.88 tok/s / 1.9439s p95**. Two replicas are required for **2× throughput** while maintaining the **2.0s p95 SLO**.


### Cost Formula

The cost per 1 million output tokens is calculated as:

```text
Cost per 1M tokens =
GPU hourly cost / (tokens/s × 3600 / 1,000,000)
```

## Knee Selection

The target p95 SLO is:

```text
p95 ≤ 2.0 seconds
```

The highest concurrency that remains within the SLO is:

```text
Knee concurrency = 8
```

At the knee:

* **Throughput:** `473.88 tok/s`
* **p95 latency:** `1.9439s`
* **Cost:** `$0.2052 / 1M tokens`
* **Errors:** `0`

Concurrency 16 achieves a lower theoretical cost of `$0.1449 / 1M tokens`, but its p95 latency is `2.4889s`, which violates the 2.0-second SLO. Therefore, it is not considered safe usable capacity.

---

## Scale-Out Plan

The knee throughput of `473.88 tok/s` is treated as the safe capacity of one GPU.

| Required Throughput | Replicas Needed | Total Cost / Hour | Effective p95 |
| ------------------: | --------------: | ----------------: | ------------: |
|   473.88 tok/s (1×) |               1 |             $0.35 |       1.9439s |
| 710.82 tok/s (1.5×) |               2 |             $0.70 |       1.9439s |
|   947.76 tok/s (2×) |               2 |             $0.70 |       1.9439s |
|  1421.64 tok/s (3×) |               3 |             $1.05 |       1.9439s |

The number of replicas is calculated using:

```text
replicas = ceil(required throughput / knee throughput)
```

Each replica is assumed to operate at the safe knee concurrency.

---

## Scale-Out Decision

For approximately **2× the current knee throughput**, two GPU replicas are required.

A single GPU cannot provide the required `947.76 tok/s` while respecting the p95 SLO. Although increasing concurrency to 16 improves raw throughput and lowers the calculated cost per token, it violates the latency target.

Therefore:

> **Scaling out with a second GPU is the correct SLO-respecting choice when throughput requirements exceed the safe knee capacity of one GPU.**
