# W4D1 — First Kubernetes Cluster

## Overview

This lab introduced the basics of running an AI serving workload on a Kubernetes cluster using the team pod's k3s environment.

The main goals were to:

* Verify the Kubernetes cluster and GPU resources.
* Diagnose common Pod failure modes.
* Deploy the serving application using the Week 2 CPU image.
* Verify the OpenAI-compatible API.
* Measure Pod startup time.
* Request and verify GPU access through the Kubernetes scheduler.

## Environment

* Kubernetes: k3s
* Node: `aidc-t10`
* Namespace: `amal`
* GPU: NVIDIA RTX A6000 48 GB
* Container Runtime: containerd
* Image: `amalk54/aidc-serving:cpu-v1`
* Model ID: `Qwen/Qwen2.5-0.5B-Instruct`
* Backend: `echo`

## Failure Mode Diagnosis

Three intentionally broken Pods were deployed and diagnosed.

### Pod A — Image Pull Error

The Pod used a non-existent image tag:

```text
busybox:this-tag-does-not-exist
```

Result:

```text
ErrImagePull
ImagePullBackOff
```

Cause: The requested image tag does not exist in the registry.

### Pod B — Insufficient CPU

The Pod remained:

```text
Pending
```

The scheduler reported:

```text
Insufficient cpu
```

Cause: The requested CPU resources could not be allocated on the available node.

### Pod C — Invalid Image Name

The Pod used:

```text
<your-user>/aidc-serving:cpu-v1
```

Result:

```text
InvalidImageName
```

Cause: `<your-user>` was a placeholder rather than a valid Docker image repository name.

The broken Pods were then removed:

```bash
kubectl delete -f broken/
```

## Pod Restart Timing

The serving Pod was deleted and re-applied to measure the time required for the echo backend to become Ready.

Command:

```bash
kubectl delete pod serving && time sh -c 'kubectl apply -f pod.yaml && kubectl wait --for=condition=Ready pod/serving --timeout=30s'
```

Measured time:

```text
real    0m2.276s
```

Therefore, the measured time from `kubectl apply` until the Pod reached `Ready` was approximately:

**2.28 seconds**

## GPU Scheduling Test

A temporary Pod was created with a request for one GPU:

```text
nvidia.com/gpu: 1
```

The Pod reached:

```text
Completed
```

The GPU was verified from inside the container using:

```bash
kubectl logs gpu-check
```

Result:

```text
GPU 0: NVIDIA RTX A6000
UUID: GPU-38b19e3a-0c6b-f90b-bb6b-35fb4d3137b1
```

This confirmed that Kubernetes successfully scheduled the container with access to the team's NVIDIA RTX A6000 GPU.

The temporary GPU Pod was then deleted:

```bash
kubectl delete pod gpu-check
```

## Key Takeaways

This lab demonstrated the basic Kubernetes workflow for an AI serving workload:

1. Verify cluster and node resources.
2. Deploy and diagnose Pods.
3. Understand scheduler failures such as insufficient CPU.
4. Run an AI serving container inside Kubernetes.
5. Verify an OpenAI-compatible API.
6. Measure Pod startup and readiness time.
7. Request GPU resources through Kubernetes.
8. Verify GPU access from inside a container.

The lab also demonstrated why correct image references, namespaces, resource requests, and readiness checks are important when operating AI workloads on Kubernetes.
