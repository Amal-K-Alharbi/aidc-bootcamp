# W4D4 — Helm, HPA, and Autoscaling

## Objective

The goal of W4D4 was to package the serving stack as a Helm chart, deploy it with Helm, configure Kubernetes Horizontal Pod Autoscaling (HPA), and observe automatic scaling under load.

The lab also included a failure analysis of CPU-based HPA on a real vLLM inference engine.

---

## 1. Metrics Server

k3s already provides Metrics Server, so no additional Metrics Server deployment was required.

Verified with:

```bash
kubectl -n kube-system get deployment metrics-server
kubectl top pods -A | head
```

Metrics were available successfully.

## 4. Resource Configuration

Because the Qwen model is loaded on CPU, the original memory limit was not sufficient.

The resources were increased to:

```yaml
resources:
  requests:
    cpu: 250m
    memory: 2Gi
  limits:
    cpu: "1"
    memory: 3Gi
```

The liveness probe was also adjusted to allow enough time for the CPU model to load:

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8000
  initialDelaySeconds: 120
  periodSeconds: 5
```

The pod successfully reached:

```text
1/1 Running
```

with zero restarts.

---

## 5. HPA Configuration

The final configuration used the **Aggressive Policy**:

```yaml
hpa:
  enabled: true
  minReplicas: 1
  maxReplicas: 5
  targetCPUPercent: 30
  scaleDownStabilizationSeconds: 30
```

Applied using:

```bash
helm upgrade team ./serving-chart \
  --set image=amalk54/aidc-serving:cpu-v1 \
  --set resources.requests.memory=2Gi \
  --set resources.limits.memory=3Gi \
  --set hpa.enabled=true \
  --set hpa.targetCPUPercent=30 \
  --set hpa.maxReplicas=5 \
  --set hpa.scaleDownStabilizationSeconds=30
```

Verified with:

```bash
kubectl get hpa team-serving
```

Final policy:

```text
Target CPU: 30%
Minimum replicas: 1
Maximum replicas: 5
Scale-down stabilization: 30 seconds
```

---

## 6. Load Test and Autoscaling

A load generator was used with 24 threads for 240 seconds.

The HPA was monitored with:

```bash
kubectl get hpa team-serving -w
```

During the test, CPU utilization increased significantly:

```text
cpu: 66%/30%   1   5   1
```

The HPA then increased the number of replicas:

```text
cpu: <unknown>/30%   1   5   3
```

and eventually reached the configured maximum:

```text
cpu: 400%/30%   1   5   5
```

Therefore, the aggressive policy successfully demonstrated:

```text
Scale-out: 1 → 5
```

After the load stopped, CPU utilization returned to normal and the deployment scaled back down:

```text
team-serving   Deployment/team-serving   cpu: 0%/30%   1   5   1
```

Therefore:

```text
Scale-in: 5 → 1
```

This demonstrates that the HPA can automatically increase capacity during high CPU load and reduce replicas after the workload ends.

## 7. HPA Failure Analysis with vLLM

A separate load test was performed against the real vLLM engine in the `team` namespace.

The vLLM pod was monitored using:

```bash
kubectl -n team top pod -l app=vllm
```

Observed CPU usage:

```text
CPU: 17m
Memory: 4175Mi
```

GPU usage was checked using:

```bash
nvidia-smi
```

The GPU showed approximately:

```text
GPU Memory: 41877 MiB / 49140 MiB
GPU Utilization: 0%
```

The vLLM engine itself was using approximately:

```text
41.9 GiB GPU memory
```

This demonstrates that CPU utilization alone may not accurately represent the workload of a GPU-based inference engine.

### Better Scaling Signals

More suitable signals for vLLM include:

* Number of in-flight requests
* Number of waiting requests
* `vllm_num_requests_waiting`
* KV-cache utilization
* GPU utilization

These metrics are more directly related to inference queue pressure, request demand, and GPU memory usage.

A reasonable starting approach is to keep request queue pressure low and tune scaling based on waiting requests or KV-cache utilization rather than CPU usage alone. The target can then be adjusted based on observed latency and workload behavior.

### Key Takeaways

* Helm packages Kubernetes resources into a reusable deployment unit.
* HPA automatically adjusts replicas based on resource utilization.
* An aggressive HPA policy can scale out quickly under heavy load.
* CPU utilization is not always a good scaling signal for GPU-based inference engines such as vLLM.
* Inference-specific metrics such as waiting requests and KV-cache utilization can provide better scaling signals.
