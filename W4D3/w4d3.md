# W4D3: GPUs in the Scheduler's Ledger

## Objective

The goal of this lab was to understand how Kubernetes treats CPU, memory, and GPU resources as a scheduler ledger.

Kubernetes schedules pods based on their **resource requests**, not their actual usage. CPU, memory, and GPUs are therefore treated as countable resources that must fit within the node's available capacity.

In this lab, I:

* Added CPU and memory requests and limits to the serving deployment.
* Intentionally requested more CPU than the node could provide and observed the scheduler response.
* Tested GPU scheduling when the only available GPU was already allocated.
* Measured the effect of unlimited and CPU-limited noisy neighbours on serving latency.
* Defined a resource policy based on the measured results.
* Deployed the team's vLLM engine on the real NVIDIA GPU.
* Verified the complete setup using the provided `verify.sh`.

---

## Step 1: Give the Serving Pods a Ledger Entry

The serving deployment was updated with CPU and memory requests and limits:

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: "1"
    memory: 512Mi
```

The resources were applied to the live deployment and verified with:

```bash
kubectl get deployment serving -o jsonpath='{.spec.template.spec.containers[0].resources}'; echo
```

Result:

```text
{"limits":{"cpu":"1","memory":"512Mi"},"requests":{"cpu":"250m","memory":"256Mi"}}
```

The deployment was also healthy:

```text
NAME      READY   UP-TO-DATE   AVAILABLE
serving   2/2     1            2
```

The important distinction is:

* **Requests** are used by the scheduler to decide placement.
* **Limits** are enforced at runtime.

---

## Step 2: Overdraw the CPU Ledger

The `impossible-cpu.yaml` pod requested more CPU than the node could provide.

The API accepted the pod, but the scheduler could not place it.

The pod remained:

```text
Pending
```

The scheduler event reported:

```text
Insufficient cpu
```

This demonstrates that an impossible resource request is not an API error and does not cause the container to crash. The pod is accepted but remains Pending because the scheduler cannot find a node where the requested resources fit.

The pod was then deleted.

---

## Step 3: Request the GPU Twice

The cluster has one NVIDIA GPU advertised by the NVIDIA device plugin.

The first GPU request was granted and consumed the available GPU. A second request could not be scheduled until the first pod released the GPU.

The important scheduler message was:

```text
Insufficient nvidia.com/gpu
```

This shows that GPUs are part of the Kubernetes scheduling ledger in the same general way as CPU and memory.

The GPU is represented as:

```text
nvidia.com/gpu: 1
```

The GPU-consuming test pod was removed before the team's engine was deployed so that the GPU was available for Step 6.

## Step 4: Noisy Neighbour Experiment

The purpose of this experiment was to compare serving latency when neighbouring CPU workloads had no CPU limit versus a `500m` CPU limit.

The burner image was changed to the team's serving image and the burner replicas were increased from 2 to 20 because the node has 28 CPU cores.

### Unlimited CPU

The unlimited burner workload was started with:

```bash
kubectl apply -f burner-unlimited.yaml
```

All 20 burner pods reached the Running state.

The latency probe produced:

```text
LATENCY n=572 fails=0 p50=2ms p95=4ms
```

### Limited CPU

The limited burner workload used:

```yaml
limits:
  cpu: 500m
```

Again, all 20 burner pods reached the Running state.

The latency probe produced:

```text
LATENCY n=572 fails=0 p50=2ms p95=4ms
```

### Comparison

| Experiment           |  p50 |  p95 | Failures |
| -------------------- | ---: | ---: | -------: |
| Unlimited burners    | 2 ms | 4 ms |        0 |
| 500m-limited burners | 2 ms | 4 ms |        0 |

There was **no measurable difference in p95 latency** in this run.

This is an honest result. The experiment did not produce a latency delta on this node. The serving pods had their own resource requests, while the burner pods were BestEffort workloads. The measured p95 remained 4 ms in both cases.

## Step 5: Resource Policy

Based on the measured results, the resource policy is:

> Serving is guaranteed to protect the p95 SLO, the dashboard is allowed to burst for short refresh spikes, and batch throttles first because it has no deadline today.

### Serving

```yaml
resources:
  requests:
    cpu: 1
    memory: 512Mi
  limits:
    cpu: 1
    memory: 512Mi
```

Serving is Guaranteed because its CPU and memory requests equal its limits.

### Batch

```yaml
resources:
  requests:
    cpu: 250m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

Batch has a lower request and a higher limit so it can use additional CPU when available but is the first workload to be throttled.

### Dashboard

```yaml
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi
```

The dashboard has a small guaranteed request but can temporarily burst during refresh spikes.

### Evidence

The serving p95 was **4 ms with unlimited neighbours and 4 ms with 500m-limited neighbours**. Therefore, the measured experiment did not show a latency penalty from the noisy neighbours on this node, but batch is still selected as the first workload to throttle because it has no deadline today.

## Step 6: Team Engine on the Real GPU

The team engine was deployed in the shared `team` namespace.

The engine uses:

```text
Qwen/Qwen2.5-1.5B-Instruct-AWQ
```

The model is the locked AWQ version from Week 3.

The canonical serving configuration includes:

```text
--dtype half
--max-model-len 4096
--gpu-memory-utilization 0.85
```

The vLLM deployment requests and limits:

```yaml
resources:
  requests:
    cpu: "4"
    memory: 16Gi
    nvidia.com/gpu: 1
  limits:
    cpu: "4"
    memory: 16Gi
    nvidia.com/gpu: 1
```

Because CPU and memory requests equal limits, the engine receives:

```text
Guaranteed
```

QoS.

The GPU was also verified from inside the container using:

```bash
kubectl exec -n team deployment/vllm -- nvidia-smi -L
```

The container successfully detected:

```text
GPU 0: NVIDIA RTX A6000
```

The team's Service is named:

```text
team-serving
```

rather than `vllm`.

This avoids the `VLLM_PORT` environment-variable conflict that can occur when Kubernetes creates a Service named `vllm`.

## Key Takeaways

### 1. Kubernetes schedules using requests

The scheduler does not place a pod based on how much CPU or memory the application currently uses. It checks whether the pod's requested resources fit within the node's available resources.

### 2. Limits are different from requests

Requests affect scheduling and resource reservation.

Limits control the maximum resources a container can consume at runtime.

### 3. GPUs are scheduler resources

A GPU is represented as:

```text
nvidia.com/gpu: 1
```

The scheduler accounts for it just like another allocatable resource.

### 4. GPU scheduling does not mean GPU memory is automatically protected

Kubernetes schedules the GPU as a countable device resource. GPU VRAM usage is not part of the normal scheduler ledger.

### 5. QoS depends on CPU and memory

Requesting only:

```text
nvidia.com/gpu: 1
```

does not make a pod Guaranteed.

The engine needs matching CPU and memory requests and limits to receive Guaranteed QoS.

### 6. The team's engine is different from the individual experiments

The individual experiments were performed in the personal `amal` namespace.

The real vLLM engine is shared by the team in:

```text
team
```

because the physical GPU is shared at the team level and the engine is the workload that will remain running for the next stage.
