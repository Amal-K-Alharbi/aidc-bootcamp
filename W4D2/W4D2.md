# W4D2 — Self-Healing Kubernetes Serving

## Objective

The goal of W4D2 was to replace a bare Pod with a Kubernetes Deployment and Service, then verify self-healing, health probes, and zero-downtime rolling updates.

The deployment uses two replicas and Kubernetes RollingUpdate strategy to maintain availability during updates.

## Kubernetes Configuration

### Deployment

The application is deployed with:

* **Replicas:** 2
* **Image:** `amalk54/aidc-serving:cpu-v1`
* **Container port:** 8000
* **Backend:** echo
* **Model ID:** `Qwen/Qwen2.5-0.5B-Instruct`

### Rolling Update Strategy

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
```

### Why these settings?

* `maxUnavailable: 0` means Kubernetes should not intentionally reduce the number of available replicas during the update.
* `maxSurge: 1` allows Kubernetes to temporarily create one additional Pod.
* Together, these settings support zero-downtime rolling updates.

## Health Probes

### Readiness Probe

```yaml
readinessProbe:
  httpGet:
    path: /health
    port: 8000
  periodSeconds: 2
  failureThreshold: 2
```

The readiness probe determines whether a Pod is ready to receive traffic.

If the Pod is not ready, Kubernetes removes it from the Service endpoints.

### Liveness Probe

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8000
  initialDelaySeconds: 20
  periodSeconds: 10
```

The liveness probe checks whether the application is still healthy.

If the container becomes unhealthy, Kubernetes can restart it.

---

## Graceful Shutdown

The Deployment uses a `preStop` lifecycle hook:

```yaml
lifecycle:
  preStop:
    sleep:
      seconds: 5
```

This gives the Pod time to terminate gracefully before it is fully stopped.

### Configuration

# Key Learnings

### Deployment vs Bare Pod

A bare Pod does not automatically recreate itself when deleted.

A Deployment maintains the desired number of replicas and automatically creates replacement Pods when necessary.

### Readiness vs Liveness

| Probe           | Purpose                                                                    |
| --------------- | -------------------------------------------------------------------------- |
| Readiness Probe | Determines whether the Pod should receive traffic                          |
| Liveness Probe  | Determines whether the application is still healthy and may need a restart |

### RollingUpdate

The combination:

```text
maxUnavailable: 0
maxSurge: 1
```

allows Kubernetes to maintain availability while replacing old Pods with new ones.

### Self-Healing

When a managed Pod was deleted, the Deployment Controller detected that the desired replica count was no longer satisfied and created a replacement automatically.
